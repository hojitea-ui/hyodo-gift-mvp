# 회고 — 용돈박스+결합상품 경쟁 분석 MVP를 만들며

## 1. 막막했던 시작 — MVP를 어떻게 쪼갤지 몰랐다

"내가 어떤 AI 전문가가 되고 싶은지"를 바탕으로 나만의 MVP(사용자가 핵심 결과 하나를 끝까지 얻을 수 있는 최소 작동 버전)를 만드는 과제가 주어졌다. 큰 프로세스 하나를 잘게 나눈다는 감각 자체가 낯설었지만, 일단 Claude Code와 함께 시도해보기로 했다.

시작은 퍼실님(Facilitator)이 올려주신 예시 지시문을 내 상황에 맞게 고쳐 쓰는 것이었다.

퍼실님 예시:
> 일단 만들고자 하는 프로그램의 PRD와 어떻게 구현할 건지 구체적인 기술명세서, 이렇게 2개를 작성하고 나서 작업을 시작할 거야. 2개 문서를 작성하는 것부터 도와줘. 문서는 마크다운 형식으로 작성할 거야.

내가 실제로 입력한 것:
> 내가 구상 중인 사업의 MVP를 만드는 게 이 세션의 목적이야. 일단 만들고자 하는 프로그램의 PRD, 그리고 어떻게 구현할 건지 구체적인 기술 명세서, 이렇게 2개를 작성하고 나서 작업을 시작할 거야. 2개 문서를 작성하는 것부터 도와줘. 문서는 마크다운 형식으로 작성할 거야.
>
> 1688에서 원물 소싱. 아이템은 작은 옥 지압봉. 원물을 패키징해서 다시 시장에 내놓을 거야. 패키징은 깔끔하고 세련된 효도 상품이라는 점에 중점을 둘 거야.
>
> 대상 구매자와 사용자가 달라. 구매자는(내 예상) 효도하고 싶은 2030 자녀들, 사용자는 50~60대 부모님들.

이어서 AI(Claude Code)가 던진 질문과 내 답:

| AI의 질문 | 내 답 |
|---|---|
| 이번에 만들 MVP의 핵심 목적은 뭐야? 사업 검증 단계에 따라 필요한 기능 범위가 크게 달라져. | 사업 전체를 놓고 보면 범위가 협소해. 내가 만들 MVP의 핵심 목적은 경쟁 상품 여러 개를 분석하고, 거기서 보이는 공통점을 도출·정리하고, 가격대와 상품 구성을 비교하는 거야. |
| 구현은 어떤 방식으로 진행하고 싶어? | 대신 구현해줘. |
| 경쟁 상품 데이터는 어떻게 수집할 계획이야? 이게 기술 구조를 크게 좌우해. | CSV/엑셀 업로드. |
| 분석 결과는 어떤 형태로 보고 싶어? | 웹 대시보드 (권장). |

이 답들을 바탕으로 PRD, TECH_SPEC 문서, 그리고 내가 조사한 경쟁 상품을 채워 넣을 `competitors-sample.csv`가 만들어졌다.

## 2. 표본 조사부터 잘못됐다

여기서 문제가 두 가지 있었다.

**첫째, 조사 방향 자체가 틀렸다.** "옥 지압봉 단독 상품"은 경쟁 상품으로서 거의 가치가 없었다. 쿠팡·네이버·아이디어스 같은 주요 이커머스에 검색해봐도 결과가 거의 없었는데, 이건 "블루오션이라 경쟁이 없는 것"이 아니라 "애초에 수요가 거의 없는 영역"이라는 뜻이었다. 이 차이를 처음엔 놓쳤다.

**둘째, MVP를 단계별로 쪼개는 이번 과제의 목표 자체를 지키지 못했다.** PRD와 기술 명세서를 쓴 뒤 스캐폴딩 → 파싱 → 분석 → UI → 검증까지 한 세션 안에 다 끝내버렸다. "작은 단위로 나눠서 확인하며 진행한다"는 원래 목적과 어긋난 결과였다.

해결 방안으로 두 가지를 고민했다.
1. 지금 프로젝트는 그대로 두고, 이후 PRD/명세서 업데이트나 새 기능은 앞으로 작은 단위로(한 파일/한 기능씩, 매 단계 왜 이렇게 짜는지 설명하며) 진행한다.
2. 아예 새 MVP를 하나 골라서, PRD 작성 단계부터 그 방식으로 다시 시작한다.

이때는 첫 번째 문제(조사 방향 오류)를 아직 자각하지 못한 채 2번을 선택해서 다시 대화를 진행했다.

> AI: PRD/기술 명세서에서 어떤 작업을 이어서 하고 싶어?
>
> 나: MVP를 "나와라 뚝딱" 하는 게 아니라 단계별로 차근차근 하고 싶었는데, 지금 뭔가 완성! 끝! 한 느낌이라 다른 MVP를 만들까 하는 생각이 드네.

그렇게 새 MVP인 "상품 구성 시뮬레이터"를 만들기로 했다. 그러나 다시 생각해보니 첫 번째 문제(지압봉 자체의 수요 부재)가 떠올랐고, 이걸 AI와 다시 짚어봤다.

> 나: 애초에 옥 지압봉은 콕 집어서 검색하는 사람이 많이 없고 괄사에 포함되는 협의의 개념이니만큼, 용돈박스+옥 지압봉으로 상품을 구성하고 상품 조사도 용돈박스 위주로 다시 해야 할 거 같아. 어떻게 할까? "상품 구성 시뮬레이터"와 "저번에 했던 결론 도출+상품 조사"(둘 다 옥 지압봉+용돈박스 기준) 중에서, 그리고 단계별로 하나씩 주고받기엔 뭐가 더 좋을까?
>
> AI: 좋은 지적이야. "용돈박스+옥 지압봉" 조합으로 바꾸는 게 맞다고 봐. 순서는 "결론 도출·상품 조사"를 먼저 하고 그 결과를 바탕으로 "구성 시뮬레이터"를 이어가는 게 좋겠어 — 구성 시뮬레이터는 "어떤 구성 요소가 원가/가격에 영향을 주는지"를 다뤄야 하는데, 용돈박스라는 새 구성요소는 아직 시세·구성 방식(봉투형/카드형/케이스형 등)을 전혀 모르는 상태니까. 지난번 옥 지압봉 단독 경쟁분석(14건)도 용돈박스 결합 상품을 다루지 않아서 그대로 안 맞고. 조사·결론 도출 쪽은 지난번 hyodo-gift-mvp와 구조가 비슷해서 새로 배울 게 적고, 구성 시뮬레이터는 마진 계산 로직·비교 UI 등 새 요소가 많아서 작은 단위로 쪼개기 좋아. 다만 지금은 데이터가 없어서 시뮬레이터부터 하면 가짜 숫자로 시작하는 문제가 있어.

이렇게 해서 조사 범위를 "옥 지압봉 단독"에서 "용돈박스+옥 지압봉"으로 넓혀 처음부터 다시 시작하기로 했다.

그런데 앞서 확인했듯, 옥 지압봉은 단독으로도 이미 수요가 거의 없었다. 여기에 "용돈박스"라는 키워드까지 결합하면 경쟁 상품 조사 자체가 심각한 차질을 빚을 게 뻔했다. 그래서 방향을 한 번 더 틀었다.

> 나: 상품 조사를 다시 할 건데, 용돈박스+지압봉 구성만 검색할 게 아니야. 용돈박스+다른 상품, 혹은 용돈박스 단독 상품을 모은 대시보드로 재구성할 거야.
>
> AI: 정리하면 — "지압봉이 있냐 없냐"를 핵심 분류 기준으로 삼겠다는 전제 자체가 틀렸다는 거네. "용돈박스"를 중심으로, 거기에 뭐가 결합되든(지압봉/다른 상품/단독) 다 조사 대상이라는 거지. 그럼 스키마도 지압봉 전용 칸을 만들면 안 되고 "결합상품이 뭔지"를 자유롭게 담는 구조여야 해. 문서 제목/컨셉을 "용돈박스"로 넓히고, 스키마의 지압봉 전용 칸을 없앤 뒤 "결합유형"(단독/지압봉/화장품/건강식품/기타 — 자유 입력) 하나로 일반화하는 방향, 맞아?
>
> 나: 아니, 단독을 빼자. 결합 유형만 두고. 용돈박스+결합상품을 조사해서 대시보드에 넣을게.
>
> AI: 그래.

이렇게 조사 범위가 "옥 지압봉 단독" → "옥 지압봉+용돈박스" → "용돈박스+결합상품 전체"로 두 번 넓어졌고, 지금의 `hyodo-gift-mvp`는 세 번째 범위를 기준으로 만들어졌다.

## 3. 세션을 쪼개서, 단계별로 다시

지금까지의 컨텍스트 윈도우를 요약해서 다음 세션으로 넘기고 이어가는 방식을 쓰기로 했다. 퍼실님이 예시 페이지에서 강조하셨듯, 한 번에 큰 작업을 뭉쳐서 구현하는 것보다 작은 작업 단위로 나눈 뒤 순서대로 구현하고 확인해야 오류가 줄어들기 때문이다.

- **세션 2**: 1단계 스캐폴딩 진행, PRD·기술명세서 초반부 작성 완료. 다음 작업(`lib/schema.ts`, `lib/parseFile.ts` 구현 + 샘플 CSV 파싱 검증)은 다음 세션으로 넘김.
- **세션 3**: TECH_SPEC 11절 기준 4단계까지 진행.
  - ✅ Next.js + TypeScript + Tailwind 스캐폴딩
  - ✅ `lib/schema.ts`, `lib/parseFile.ts` + 샘플 CSV 검증
  - ✅ `lib/storage.ts` (localStorage 래퍼)
  - ✅ 업로드 화면 (UploadPanel)
  - ⬜ `lib/analysis.ts` (가격 통계, 히스토그램, 빈도/교차표)
  - ⬜ 대시보드 화면 (요약 카드 → 차트 → 테이블)
  - ⬜ 전체 흐름 수동 테스트
- **세션 4**: 남은 5~7단계 진행. README.md 작성만 남김(TECH_SPEC 9절 기준: 프로젝트 개요, 실행 방법, 샘플 데이터 안내, 스크린샷, 폴더 구조/핵심 로직 위치).
- **세션 5**: README.md 작성 완료. 핵심 단계인 경쟁 상품 실제 데이터 조사 및 `competitors-real.csv` 작성 완료(이전 과정과 다르게, 샘플 파일을 덮어쓰지 않고 별도 파일로 생성). 남은 작업을 체크리스트로 정리:
  - A. 최종 CSV 대시보드 업로드 → 정상 동작 확인 → 업로드/대시보드 화면 캡처 → README 삽입
  - B. 결론 보고서 + 상품구성 비교 작성 (AI 담당 — 대시보드 결과를 보고 작성)
  - C. Main Quest 01 제출자료: 서비스 한 문장 / AI 대화기록+베스트 프롬프트 / 회고 (같이 초안 작성)
  - D. GitHub 저장소 생성 (본인이 직접) + push
  - E. Vercel 배포
- **세션 6**: 작업 A 완료.
- **세션 7**: 작업 B 완료. 걸어온 과정을 되짚는 이 회고는 내가 먼저 초안을 쓰고 AI에게 보완을 맡기기로 했다 — 지금 보고 있는 이 문서가 그 결과물이다.
- **세션 8** (지금): 작업 C·D·E를 마무리했다. GitHub 저장소 생성과 Vercel 계정 가입은 직접 했고, 그 다음 저장소 연결부터 배포·동작 확인까지는 AI에게 맡겼다. 서버·DB가 없는 구조라 별다른 설정 없이 한 번에 배포됐고, 배포된 사이트에 실제 데이터를 다시 올려 정상 동작까지 확인했다. 이걸로 세션 5에서 세운 체크리스트(A~E)를 모두 마쳤다.

## 배운 점

1. **"경쟁이 없다"와 "수요가 없다"는 다르다.** 검색 결과가 적다고 곧바로 블루오션으로 해석하면 안 된다. 옥 지압봉 단독 조사에서 이 구분을 놓쳤고, 그 대가로 조사 범위를 두 번이나 다시 넓혀야 했다.
2. **작업을 쪼개겠다는 결심만으로는 부족하다.** 세션 2에서 "단계별로 하겠다"고 마음먹었지만, 실제로는 스캐폴딩부터 검증까지 한 세션에 다 끝내버렸다. 의도와 실행 사이의 간극을 줄이려면, 세션을 시작할 때 "이번 세션에서 할 일"을 미리 한 줄로 못 박아두는 편이 나을 것 같다.
3. **전제가 틀렸을 때는 되돌아가는 비용을 아까워하지 않는다.** "지압봉 유무"를 핵심 분류 기준으로 세워뒀다가, 대화 중에 그 전제 자체가 잘못됐다는 걸 깨닫고 스키마까지 되돌려서 고쳤다. 처음 세운 구조에 얽매이지 않고 전제를 다시 점검한 게 결과적으로 더 넓고 정확한 조사(20건, 결합상품유형 12종)로 이어졌다.
